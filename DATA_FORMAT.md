# Формат данных для ранжирования API

Этот документ описывает согласованный формат передачи данных и внутренний интерфейс ранжировщиков. Это целевая схема проекта, а не утверждение о структуре исходного ToolLens.

## Таблицы

Предпочтительный формат для передачи — Parquet; допустим CSV в UTF-8 с заголовком. Три таблицы могут храниться отдельными файлами.

### `apis`

| Поле | Тип | Описание |
| --- | --- | --- |
| `API_id` | int64 | Уникальный неотрицательный стабильный идентификатор API |
| `description` | string | Текстовое описание API |

Каждая строка представляет один API. `API_id` не обязан быть непрерывным или совпадать с номером строки. Состав описания следует согласовать: он должен одинаково подготавливаться для всех методов.

### `requests`

| Поле | Тип | Описание |
| --- | --- | --- |
| `Request_id` | int64 | Уникальный неотрицательный стабильный идентификатор запроса |
| `text` | string | Текст запроса |
| `split` | string | `train` или `test` |

Каждый запрос принадлежит ровно одному split. Разделять нужно по запросам, не разрывая их взаимодействия. Правила обработки дубликатов и выделение validation из train согласовываются до эксперимента.

### `interactions`

| Поле | Тип | Описание |
| --- | --- | --- |
| `Request_id` | int64 | Ссылка на запрос |
| `API_id` | int64 | Ссылка на API |
| `relevance` | число | Конечное числовое значение; положительное означает релевантность |

Одна строка описывает одну пару запрос–API; повторяющиеся пары необходимо разрешить до передачи. Неуказанная пара считается неизвестной, а не подтверждённо нерелевантной. Все ID взаимодействий должны присутствовать в соответствующих таблицах. Обязательные поля не должны содержать null; пустые строки и их смысл нужно согласовать отдельно.

## Разделение и оценка

- При `fit` доступны только train-запросы, их train-взаимодействия и API с положительными train-связями.
- Тестовые запросы и метки не участвуют в подготовке моделей. На этапе инференса доступен полный каталог API; `prepare_candidates` принимает описания, но не метки.
- Один и тот же API может быть релевантен запросам из обоих split. Результаты теста считаются по test-взаимодействиям.
- BM25 использует статистики train API; BGE кодирует описания кандидатов при инференсе без дообучения весов; Popularity не имеет истории для API без train-связей.

## Представление в Python

```python
corpus = {12: {"description": "Find weather by city"}}
requests = {31: "Find the weather in Paris"}
train_qrels = {31: {12: 1.0}}
```

`fit(corpus, train_qrels, train_queries=requests)` принимает train-корпус, связи и тексты train-запросов. CF требует `train_queries`, включая запросы с пустым списком позитивов. Бейзлайны могут игнорировать этот аргумент. `prepare_candidates(full_corpus)` подготавливает полный каталог. `predict(text, top_k)` возвращает упорядоченный список целых `API_id`.

Для CF отсутствующая связь внутри train-матрицы имеет целевое значение 0 согласно выбранной постановке эксперимента. В MSE все такие пары входят в функцию потерь. В BPR негативы выбираются среди train API без позитивной связи с запросом или семейством. Это модельное допущение фиксируется отдельно от исходной разметки.

Кэш `train_query_embeddings` сопоставляет ровно train Request_id с векторами одного замороженного энкодера. Для семантических негативов `train_api_embeddings` сопоставляет train API_id с эмбеддингами описаний. Обе матрицы должны иметь одинаковую размерность и совместимую ревизию энкодера. Код проверяет ID, форму и конечность значений. Ревизию и подготовку текста фиксирует вызывающий эксперимент. На инференсе можно использовать `predict_from_embedding` с эмбеддингом того же энкодера.

Для эмбеддингов и численных операций подходит массив NumPy `float32`, а для большой разреженной матрицы взаимодействий — SciPy CSR. Индексы строк и столбцов должны иметь явные обратимые отображения на `Request_id` и `API_id`; сами ID не используются напрямую как индексы.

Исходные строковые ID ToolLens нужно преобразовать в целые без коллизий и сохранить версионированные таблицы соответствия исходных и внутренних ID. Если ID не являются десятичными числами, следует построить стабильное отображение. В ноутбуке `synthetic_ranker_experiment.ipynb` есть `adapt_tables` для уже загруженных pandas DataFrame: он проверяет поля, связи и split, но самостоятельно файлы не читает.

## Сохранение моделей

Текущие ранжировщики сохраняют модель в новый каталог в `model.json`, формат версии 2 с числовыми ID. Сохранённое train-состояние не включает подготовленный на этапе инференса каталог кандидатов: после загрузки необходимо снова вызвать `prepare_candidates`.

Модели CF имеют собственный формат версии 1. Конфигурация и история потерь записываются в `model.json`, числовые ID, факторы, train-эмбеддинги, соответствие семейств и CSR-матрица — в `factors.npz`. NPZ загружается с `allow_pickle=False`. Веса BGE доступны через локальный путь или переданный энкодер. Каталог кандидатов после загрузки CF также передаётся заново.
